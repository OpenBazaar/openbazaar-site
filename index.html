01 / INDEPENDENT BY DESIGN

Your store isn’t
someone else’s
account.

The original OpenBazaar idea still holds: a buyer and a seller should be able to trade without handing the relationship to a platform.

Read the design paper →
01

Publish under your own key.

A store’s identity is its public key. Store and listing records carry the seller’s signature, so recipients can verify the data independently of whoever served it.

02

Keep the conversation between peers.

The catalog is public. Orders are sealed to a vendor and transported over Tor. Shipping details belong in the order, not in a public listing database.

03

Operate the software yourself.

The desktop app runs its own node. An always-on home node can keep your store available and be managed by paired devices over Tor.

No marketplace login to lease. No platform wallet to trust.
Software you can inspect, run, and change.

BIP 340 / SHA-256

Verify the seller, not the server.

Your node checks store and listing signatures. A listing’s content hash identifies the exact version an order refers to. A valid signature proves authorship and integrity; it does not prove freshness, availability, or an honest seller.

The node holds spend keys and trade state. Local clients use loopback; paired remote devices use the home-node channel. Architecture reference ↗

03 / UNDER THE HOOD

Open protocols.
Explicit tradeoffs.

Decentralization is a set of engineering choices. Here’s what the current implementation does, and where its boundaries are.

Inspect the implementation ↗
IDENTITY & DATA INTEGRITYSigned stores and listings+

BIP 340 Schnorr signatures authenticate canonical record bodies. A listing address is the SHA-256 hash of its body, and an order commits to that address. A signature doesn’t guarantee the goods, the seller, or the latest price.

Read the record implementation ↗
PRIVATE ORDER TRANSPORTTor between trading nodes+

Sale endpoints accept loopback HTTP or a v3 onion reached through the node’s Tor client. Clearnet sale hosts and redirects away from the onion are refused. This does not make all node traffic anonymous; chain, rate, and optional service configuration also matter.

Inspect the transport boundary ↗
BITCOIN ESCROW / TESTNET4 DEMOTwo spend keys. A bounded moderator.+

Escrow aggregates only the buyer and seller keys into a 2-of-2 MuSig2 Taproot output. The moderator can release a share for a presigned outcome; it has no spend key in the output and cannot choose an arbitrary payout. The silent case is the buyer’s presigned refund at the agreed height.

Mainnet moderated escrow is refused pending protocol review. Direct pay does not provide escrow protection.

Read the escrow protocol ↗
DISCOVERY / AN EXPLICIT TRUST DEPENDENCYSigned introductions, direct follows+

Bundled introductions supply directory data verified under a shipped key. That is a discovery trust dependency, not a permissionless DHT. A node can disable introductions and follow a store’s onion address directly; doing so removes directory discovery and announcements.

Inspect directory replication ↗
SELF-HOSTINGA home node you can pair with+

An always-on node exposes a restricted Tor admin service to paired devices. Each device has its own key and signs requests; spending also requires the wallet passphrase and a spend ticket. An optional encrypted LAN channel supports local access.

Home-node setup and threat model ↗
REPUTATION / PUBLIC PROOFSA count and a time-locked bond+

Finished escrow payouts contribute to a store’s count. A new seller needs a passing bond to start escrow: at least 10,000 sats locked for at least 2,016 blocks. The bond remains spendable only by the store key after its lock; there is no slash key. These are testnet4 mechanisms.
